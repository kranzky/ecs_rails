# RFC-0016: Markers on a shared table — `marker`

**Status:** Implemented (2026-09-04, Linear ECS-16)
**Depends on:** [RFC-0009](0009-component-presence.md) (presence), [RFC-0014](0014-plural-components.md) (slots)
**Decision:** [ADR-0018](../adr/0018-catalogue-in-the-gem.md) §4, amending [ADR-0009](../adr/0009-component-presence.md)

## Goal

A marker — a component with no state, whose presence is its whole meaning —
needs no table of its own. All markers are rows in one `markers` table created
at install; the slot is the marker name.

```ruby
class User < ApplicationEntity
  marker :moderator
  marker :administrator
end

user.add(:moderator)            # a row: (user.id, "moderator")
user.moderator?                 # => true
user.moderator = false          # removes it; `= true` adds
user.remove(:moderator)
User.with_marker(:moderator)
User.without_marker(:administrator)
```

## Rules

- **`marker :moderator` is `component Marker, prefix: :moderator, delegate:
  false`.** `Marker` is the application's one-line catalogue class including
  `EcsRails::Catalogue::Marker` (table `markers`: `id, entity_id, slot,
  timestamps`, `UNIQUE (entity_id, slot)`, cascading FK), written by
  `ecs_rails:install` and found by name via `EcsRails.config.marker_class_name`.
- The declaration generates, on top of what `component` generates (the reader
  `moderator_marker` and its predicate `moderator_marker?`), the **bare
  predicate `moderator?`** — `has?(:moderator)` — and the **Boolean writer
  `moderator=`**, which `add`s on a truthy value and `remove`s otherwise, cast
  as ActiveModel casts Booleans so a checkbox param routes through flat mass
  assignment.
- **`add` / `has?` / `remove` accept a Symbol** naming a declared marker, with
  no `prefix:`. An unknown name is `InvalidComponent`, listing the entity's
  markers. The component form (`add(Marker, prefix: :moderator)`) still works.
- **Presence semantics are RFC-0009's, unchanged.** A marker is never dirty, so
  the save cascade never writes it; `add` writes now; `remove` destroys now.
- **`with_marker(name)` / `without_marker(name)`** are sugar over
  `with_component(Marker, prefix: name)` / `without_component`, entity-model
  scoped like every component query, so two entity types sharing a marker name
  do not leak.
- **The marker name reserves `name?` and `name=`** on the entity
  (`ecs_reserved_names`), and `marker` refuses a name whose predicate or writer
  an existing component, relationship or marker already owns
  ([ADR-0004](../adr/0004-delegation-conflicts-raise.md)). The same marker
  twice is a `DuplicateComponent`.
- Subclasses inherit markers; `marker_names` walks the ancestry; markers
  survive a reload like any declaration.
- **A zero-attribute component on its own table still works** (ADR-0009's
  original shape — the gem's `Moderator` fixture). `marker` is the shape that
  needs no migration.

## Generator

`ecs_rails:install` creates `markers` and writes `app/entities/components/marker.rb`.
`ecs_rails:upgrade` gains a third job: create `markers` if missing, and move
every pre-0.3 marker table — recognised as a component table with no attribute
columns at all — into it under the table's singular name, then drop it.
Irreversible, written as `up`/`down`; the developer reviews the list.

## Tests

`spec/markers_spec.rb`: the contract (add/has?/remove by name, the row, the
cascade never writes, the component form, idempotence), the declaration (slot,
reader, options, names, duplicates, the missing-class error), the writer
(true/false, form strings, mass assignment), collisions both ways, undeclared
names, querying (sugar equivalence, no cross-entity leak), preloading via
`includes_components(Marker)`, reload.

## Non-goals

- A marker with data. That is a component (`Role`, `Discard`), not a marker.
- Dynamic markers not declared on the class.

## Notes from implementation

- `moderator_marker?` is still generated by `component` alongside the bare
  `moderator?`. Harmless, and suppressing it would special-case the DSL.
- The upgrade heuristic "no attribute columns" is exactly the marker shape;
  `markers` itself is excluded by name. A bespoke empty component the app wants
  to keep on its own table should be removed from the generated migration
  before running it.

**Demo verdict.** `Moderator` and `Administrator` — two component files, two
specs, two tables, two migrations — became two lines on `User`. Controllers
call `user.add(:moderator)`; the views' `user.moderator?` did not change. See
the [friction log](../friction-log.md).
